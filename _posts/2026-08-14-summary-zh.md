## [“Spaghettifying DRAM”攻击：借 DRAM 解锁隐藏 CPU 功能](https://github.com/xoreaxeaxeax/skitter-creek-bath-salts) ⭐️ 8.0/10

安全研究员 Christopher Domas 发布了名为“Spaghettifying DRAM”的硬件攻击方法，利用 DRAM 修改 CPU 配置寄存器，从而解锁未公开的 CPU 功能。演示针对 AMD Family 16h（Jaguar）处理器，展示了如何通过写入“xor dword [0xf80c2094], 0x00400000”来翻转特定位。 该技术揭示了 DRAM 可能成为访问隐藏 CPU 功能的入口，使拥有 ring-0 权限的攻击者能够在底层危及系统安全。若 Xbox、PlayStation 等游戏主机使用受影响的 AMD 处理器，其依赖的 CPU 安全边界可能尤其脆弱。 该攻击在 AMD Family 16h（2013 年的老款低功耗架构）上演示，通过直接访问内存映射的配置寄存器实现。README 指出，Zen 3 的寄存器基地址不同，因此该攻击对更新处理器的有效性仍是个未解问题。

hackernews · matt_d · Aug 13, 14:17

**背景**: DRAM（动态随机存取存储器）是计算机中的主要易失性存储器，通过需要定期刷新的电容来存储数据。CPU 通常包含官方文档中未记录的隐藏功能和寄存器，有时是为特定客户添加的。该攻击表明，攻击者可以通过操纵 DRAM 来修改这些隐藏的配置寄存器，从而绕过正常的安全边界。这一技术与此前关于未公开 CPU 行为和 Rowhammer 式攻击的研究有关。

## [单条日志导致 journald 写入 49KB+ 磁盘数据](https://github.com/systemd/systemd/issues/40262) ⭐️ 7.0/10

GitHub 上的一个问题报告了 systemd-journald 的严重写放大：一条日志在 ext4 上可触发超过 49KB 的磁盘写入，在 btrfs 上超过 110KB。该问题还指出，现有的过滤选项过于有限，无法有效控制日志刷屏。 这关系到系统管理员，因为写放大会加速 SSD 磨损，并可能降低繁忙服务器的 I/O 性能。它也让 Linux 日志架构的讨论更加热烈，journald 的索引开销正受到越来越多的质疑。 写放大源于 journald 的追加式、基于 mmap 的文件格式，每条日志都会重写元数据和索引结构。目前只能通过按级别过滤，或转发到 rsyslog 再过滤来缓解，因为不支持按单元或按字段截断日志。

hackernews · ValdikSS · Aug 13, 18:41

**背景**: systemd-journald 是一个系统服务，用于收集并以结构化、带索引的日志文件存储日志数据，数据来源包括内核消息、syslog 和服务输出。其日志格式受 git 仓库启发，通过在文件末尾追加数据来保证健壮性，但这一设计带来了显著的每条日志元数据和索引开销。Journalctl 是读取和过滤这些日志的标准工具。

**社区讨论**: 评论者大多对 journald 持批评态度：有人称它是“systemd 生态中最糟糕的部分”，建议只将其用作路由器；还有人抱怨 KDE 的 kio 等应用会刷入数十万条无价值的日志。其他人指出，除按级别过滤外几乎不可能过滤，而且原始设计意图并未预料到这种写放大。
